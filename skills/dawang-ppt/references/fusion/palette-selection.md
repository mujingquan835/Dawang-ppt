# 配色推荐与确认

这是自主制作中的一次配色交互。材料与用途、简短大纲明确后执行；详细内容策划、排版、编辑保存与验收继续沿用原制作流程。

## 何时询问

| 本次情况 | 动作 |
|---|---|
| 已指定配色、完整品牌规范，或沿用已确认方向 | 直接执行，不重复询问 |
| 用户明确委托“配色你定”“不用确认直接做” | 自动匹配并采用，在制作说明中简短记录选择依据 |
| 修改已有稿件，未要求换色 | 沿用旧稿；局部标题强调仍受品牌和锁定范围约束 |
| 新建或视觉重构，尚未确定配色，也未委托自动决定 | 提供适配候选及实际配色预览，等待用户选择后再制作正式幻灯片 |
| 用户要求更换配色，但没有给出具体方向或委托 | 提供候选供选择，保留原稿；确认后只改获授权的范围 |
| 用户明确要求原样dashi主题模板 | 使用既有模板兼容入口；主题已指定时不另问配色 |

“工作汇报”“产品发布”等用途用于匹配候选，不视为用户已经选定配色。用户明确的完整配色可以直接沿用；只给出“蓝色”“活泼一些”等宽泛倾向时将它作为候选依据。已有品牌规范无法覆盖的细节可按规范自主设计，不要求用户逐个确认颜色。

## 如何匹配与展示

先看受众、使用场景、正式程度、阅读方式、图片和数据量、品牌及素材自然色。**主选候选从[九组汇报配色](report-layout-logic.md#2-颜色职责一深一浅一跳)中挑**（用户确认 2026-11-04：场景文档自带的配色参考不够好看，不作主选），按各组的适用说明挑 3–4 组。有品牌色或用户点名时以其为准；场景文档配色参考、[dashi完整主题索引](dashi-theme-references.md)、当前素材只在用户要求或九组都不适合时补充，并说明原因。场景文档中关于拒绝平庸配色、背景明度的建议仍然参考。场景关键词只是检索提示，不固定绑定主题；候选应有可辨认且适用的差异，通常提供3—5组，实际不足时少给，不为凑数加入不适合的方案。

展示候选的序号、名称、适配理由及实际配色预览。预览中能看到背景、标题与重点词、正文、辅助文字及结构面之间的关系，不能仅列名称或HEX，也不能用四组示意或旧六种适配外观代替本次匹配。引用原主题时先看相关实际页面，并核对源码色值；页面中有多组配色或深浅变体时指出本次借鉴哪一种。使用转译后的色值时说明为改编方案，不称原版精确复刻。

九组汇报配色在候选 JSON 里直接写 `{"report":"blue-gold","reason":"本次适配理由"}`，名称、色值和来源自动补全，预览画成迷你汇报页（章节标签页头、主色答案块、目标→实际对照组、只在最高项用跳色的色块），能看出一深一浅一跳在页面上的面积分工。可运行 `node <skill>/scripts/palette-preview.mjs <本次候选.json> <临时预览.html> --png <临时预览.png>` 生成统一结构下的颜色应用示意，实际看图后将PNG与选项理由提供给用户。输入由制作智能体整理，不要求用户编写JSON：`{title, options:[{id,name,reason,source,palette:{bg,ink,accent,muted,line,surface?}}]}`；颜色为HEX，`source`记录具体原版页面、品牌或自主设计依据。工具只展示已整理的颜色，不自动判断适配性或推断来源。渐变、多色等效果可补充对应真实页面预览；工具的纯色示意不是表达上限。

配色询问可与简短大纲确认合并为同一次回复。发出选项后先等待答复；可整理材料与事实，不生成最终页面、不擅自选定方案，也不因等待时间长而自动确认。用户回复序号或名称后，复用原候选及其含义，不重新打乱编号；不明确时只澄清所指选项。

## 选择后继续制作

在原逐页提纲或制作决定中记下选项ID、颜色职责与来源，沿用本次确认；不增加必填工程字段。随后按已读取的制作、通用与主场景规则完成内容策划和自主排版。dashi配色选择不是指定原规则的设计系统，不自动触发额外设计系统读取。

确认的是全稿颜色职责和视觉方向，版式、信息关系和页序仍由内容决定。明暗页面、图表分类和必要自然图片色可按内容适配，保持品牌、状态和数据含义；需要改变已选方向时说明具体原因再确认，不默默换成另一套。后续检查对照原材料、已选配色与当前编辑范围，保留所有必需事实、证据、表格和限定。

正式交付继续默认一个可离线编辑保存的HTML。配色预览与候选JSON属于临时选择材料，不自动加入最终交付目录或正文页面。未指定、已指定、委托自动决定、旧稿局部修改和原样模板应分别遵守本页分流条件，不套用同一询问步骤。
