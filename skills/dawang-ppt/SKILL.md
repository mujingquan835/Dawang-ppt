# Dawang-PPT

## 分工

- **设计依据：** 完整制作规则（制作步骤、通用规则、场景文档，用户指定时加设计系统）。由 `rules:read` 读取本机锁定版本的原文，每节标注 apply（照做）/ adapt（按 note 的边界执行）/ replaced（由 Dawang 引擎替代，多为 PPTD 格式与导出）。这些标注就是 Dawang 引擎对原规则的全部改动。
- **Dawang 提供：** 网页工作台（编辑、保存、导出）、authored 工程格式、规则锁定、程序检查与独立复核，以及用户确认过的几项交互（配色预览、重点句、单 HTML 交付）。
- **优先级：** 用户明确要求 > 本文件写明的流程（如先出第一版、页数不提问）> 原规则（apply/adapt）> Dawang 补充做法。Dawang 补充只填原规则未覆盖的细节，冲突时按原规则。引擎做不到的效果明确报告，不静默降级。

用户用自然语言提交材料；工程 JSON 和 CLI 都由制作智能体完成。保留原规则阅读、逐页设计与看图，不降低模型思考档位。

## 主线

**理解信息关系 → 自主设计 → 验证表达。** 其他步骤都服务这三件事。

- **理解信息关系：** 读懂事实之间是什么关系，哪些关系材料里没有。产物是 `outline.json` 和一份关系缺口。
- **自主设计：** 按关系选结构，直接做完第一版，不等用户确认。产物是可编辑的 HTML。
- **验证表达：** 程序检查、看图和独立复核，确认页面表达的关系与材料一致。

第一性是先交出一版。缺材料、页数未定、配色未选都不是停下的理由。

## 默认制作流程

按原规则的制作步骤执行，Dawang 只在对应步骤插入引擎操作。

**一轮做到底：** 收到材料后，同一轮内一直做到 `publish:html` 成功，先交出第一版。只有四种情况可以停：命令报错且自己修不好；只给了主题、没有任何可上屏的材料（先问一次）；用户明确要求先确认大纲或配色；第 3 轮复核后仍有阻断。其他情况不得以“尚未完成”收尾。停下时说清停在哪一步、哪条命令或哪条意见、要用户做什么。

0. **环境：** `node <skill>/scripts/dawang.mjs doctor`，核对 skill/project 路径、installations、rules（status 应为 pinned）与 ready（应为 true）。规则资料由 `DAWANG_PPT_RULES_DIR` 或 `~/.dawang-ppt/production-rules/` 提供，版本由 `references/production-rules.lock.json` 固定；缺失或不一致时停止并告知用户，不回退到摘要或简化规则。开发源码与日常安装可能不同，不据仓库改动宣称已安装。首次检出 `npm ci --prefix skills/dawang-ppt/project`。
1. **读材料（原规则 step1）：** `prepare <材料> <新目录> --scenario <id>` 提取正文、原图台账与该场景规则，材料可以是 PPTX、Markdown、文本或本产品 HTML/JSON（PPTX 按页抽文字、表格、备注和图片，Markdown 里的图片也进台账）；实际阅读 material.json、rules.json 并查看必需图片。完整读取用户材料，不擅自联网扩充，不补造数据。
2. **理解信息关系（原规则 step2，新建必做）：** 先判断事实之间的关系：目标↔实际、动作→结果、结果→原因、问题→措施、措施→负责人与时间、多页事实→总判断；述职再看职责→业绩、业绩→个人贡献。结构跟着关系走，缺的关系记下来。不论用户给的是大纲、一段文字、文档还是图片，都整理成结构化大纲 `outline.json`（格式见 [工程编写速查](references/authoring-api.md#内容大纲)）：汇报类型（工作汇报/复盘为 `report`，述职为 `review`）、统计时期、每页角色（整体结论、成果数据、关键动作、资源支持、问题差距、原因复盘、下一步、需支持/决策、职责定位）、重点句、带单位的数据、要点和照片。大纲写明 `scope`：用户只要一部分页面或某一块内容时为 `part`（默认），用户要把整份材料做成一份汇报/述职时是 `full`；authored 工程的 `requirements.scope` 同步填写。汇报结构要写进对应字段，页型才能被建议出来：有目标值写 `data[].target`（与实际值成对），今年/去年、亮点/待改进等成对内容写 `compare`，按月/季度展开写 `periods`，多张照片各对应一项时把事项写进 `items`（与 `photos` 同序同数量），带标签的一句话内容写 `statements:[{id,label,text,from}]`（没有单位的短语式结果也放这里，加 `asMetric:true`，不要放 `data`）。然后运行 `outline:check <outline.json>`：输出 `relationGaps`（关系缺口候选）和每页建议页型。`part` 只看所做页面的关系，`full` 才看整稿结构（整体结论、问题差距、下一步）。候选由程序按结构找出，是否成立要回到材料判断，程序看不出的关系自己补上。`rules:list` 查场景 ID，选主场景（工作汇报一般为 management-report）。
   **页数按原规则 step2 定：** 用户指定页数优先；给了逐页大纲或讲稿时按其页数；其他情况按内容量自行估算，交付时说明，不提问。
   **关系缺口不拦第一版：** 不为缺口提问或等待，继续往下做。
   - **用户没有授权补写：** 只用材料已有内容，缺关系的地方按现有信息排好。页面不写“材料未提供”，缺口放进交付回复。
   - **用户说“可以适当撰写”或类似授权：** 第一版直接把缺的部分写上，用户之后自己改。结论、原因、动作、下一步等文字写全；材料里没有的具体数字写 `XX`（如 `XX 单`、`XX%`），版式按真实数字排好。原话记入 `userDecisions`，补写内容写 `from:{locator:'用户授权补写',excerpt:用户原话}` 和 `status:'estimated'`。页面任何位置（含页脚来源行、表头、小标题）都不出现“补写”“授权”“待验证”“建议”这类制作标记。补写和展开的内容由工具自动标在两处，投屏时都看不到：网页编辑器选中该元素时侧栏提示“模型补写，请核对”，导出 PPTX 时写进该页演讲备注。不用手写备注，也不在页面上另加标记。
   - **前置说明：** 用户要求先看缺口时可以放在出稿前，说法和交付回复相同（见第 9 步），并说明不回复也会按现有材料出稿。不影响制作的发现（如材料内部数字矛盾）在交付时单独说明。
   按大纲制作时，每页沿用大纲里的重点句、数据与照片，并按 `outline:check` 建议的页型和组件起步。[汇报版式逻辑](references/fusion/report-layout-logic.md)已拆成可放进任何区域的组件（答案块 `answerBlock`、对照组 `comparePair`、左右对照 `contrastPair`、时期色带 `periodBand`、指标带 `kpiStrip`、反白色块、深色侧栏），按页面角色默认使用，不要求材料数字与模板对上。每页 `visualDecision.pattern` 写所用页型；自由组合写 `free：理由`，由区域设计说明各区域如何帮助读者理解；封面、目录、章节页写 `waived`，用户决定不用组件的写进 `userDecisions`。
   **大纲整理好后建立事实基线（新稿必做，由制作智能体完成，不问用户）：** 大纲顶层写 `sources`，每项事实写 `from:{locator,excerpt}`（原文位置与摘录）；版面结构看不出的关系（因果、支撑、归属等）写进 `relations`，取舍写进 `dispositions`。关系缺口只进交付回复，不写成假关系。流程、对照、时期和表格的关系由工具按结构生成，不从措辞推断。运行 `outline:baseline <outline.json> <新目录>`，得到 `content-baseline.json` 与 `authored-scaffold.json`（已带四项内容契约和每页 `requiredRefs`）。`outline:check` 的 `baselineIssues` 由制作智能体补全，不问用户。排版不能改基线；内容修订先审查来源，在新目录生成新版本。
3. **读规则，先列清单：** 实际阅读 `rules:read <主场景>` 返回的 apply/adapt 原文（本会话已读过同场景同指纹可复用）。原文与锁定版本不一致时停止并告知用户。随后运行 `rules:checklist <主场景>`，在排版前按章节写下这一章的要求打算怎么落实、落在哪页，或为何不适用（见“规则清单”）。设计从这份清单出发，不是排完再补记。
4. **配色：** 按 [配色推荐与确认](references/fusion/palette-selection.md) 处理：未指定且未委托时，按内容从九组汇报配色里选最合适的一组直接做第一版（用户确认，场景文档自带的配色参考不作主选），不等待。再挑 2–3 组用 `palette-preview` 的 `{report:'blue-gold'}` 生成迷你汇报页预览，随第一版一起给用户，用户选别的就整稿换色。规则清单的配色参考章节记为 `applied`，`how` 写所选配色的颜色分工并引用 HS-04（红金不用于大促/促销类复盘，三原色不用于正式汇报，三原色同页不加紫绿，见 HS-05）；已指定、已委托或旧稿局部修改不给预览。
5. **文案与提纲：** 按场景规则对标题、内容的要求和 [文案编辑](references/fusion/content-editing.md) 主动改写，先形成可上屏文案再排版。**用户给的是逐页写好标题和内容的定稿大纲时，大纲视为用户明确要求：** 原句完整保留（keyLine 记 `quoted`），表头不改，页面不写字体规范、测试说明等内部信息。在原句之上主动把重点提出来：每条内容配 2–6 字短标签，每组内容配模块名和一句概括；`X：结论` 式标题把 X 放到眉标、结论做大标题。可以适度展开用途或效果说明，但不得新增数字、案例、人名；含展开内容的条目 `from.locator` 写 `制作者展开`、excerpt 写依据的原句、`status:'estimated'`，交付时逐页列出请用户核对。**文字口径：** 标题里的数字必须出现在本页（封面的出现在某一页），并带着原文的限定（哪一场、哪个店、哪个月）；“连续两年”这类说法要在本页放出每一期的数；同一件事、同一个数字全稿一个说法、一个目标。`outline:baseline` 拦下标题数字缺失，`outline:check` 的 `wording-*` 提示逐条对照材料处理，细则见[文案编辑](references/fusion/content-editing.md#内容取舍与证据)。详见第 6 步的组版器说明。
6. **排版（原规则 step3）：** 依据清单与场景规则视觉要求逐页设计，写 authored 工程（`styleId:"authored/custom"`，1920×1080 逻辑画布）。排版前实际读取 [Dawang补充做法](references/fusion/visual-authoring.md) 与 [汇报版式逻辑](references/fusion/report-layout-logic.md)：禁止卡片不等于只用文字，每页用尺度对比、结构图、证据画面、视觉母题或色面分区之一承担主视觉。用 [排版工具与页型](references/authoring-api.md#排版工具与页型) 写工程：网格、指标组、流程、编号列表、图片网格与表格由工具保证对齐与成组，不手算坐标；先按每页内容选页型或自行组合工具，再调整。每页写 `visualDecision`，含 `zones` 分区（页型会给出初稿，按实际构图修改）；排版后运行 `wireframe <authored.json> <临时目录>` 看分区线框，确认主次区域与留白合理再进入生成。图片用文件路径作 `src`（或登记到 `media.entries` 后用 `mediaRef`），不把照片写成 data URI。工程从 `authored-scaffold.json` 开始，存为同目录的 `authored.json`。骨架已按大纲搭好每页的区域和待填绑定，补上区域的 `bounds`、面板元素、设计理由，把 `bindings` 的 `elementIds` 填成实际元素。写法照 `examples/report-contract.mjs`（能通过 `make` 的完整示例），不读引擎源码猜结构。面板按内容取高；无底框的文字组用 `openGroup:true`，不为对齐而画满矩形。表格、流程、角色、排期优先用 `capacity-kit.mjs` 的实测模块（`measureModule`），不静默删字或缩字。细节见[内容关系与页面绑定](references/content-page-contracts.md)、[独立基线与组合布局](references/composition-contracts.md)和[模块与容量处理](references/capacity-modules.md)。
   **工作汇报默认用整稿组版器：** 制作者负责把内容和关系写进大纲，版面交给 `composeReportDeck`（`authoring/report-deck.mjs`）。它负责页头、模块顺序、等高、列宽、字阶、图片分栏、对齐和区域绑定，不手算坐标。照 `node <skill>/examples/report-modules.mjs <新目录>` 写，只有组版器表达不了的页才手写，手写页同样要满足下面的标准。
   - **目标：** 读者只看标题、标签和加粗，就能说出本页逻辑。
   - **大纲字段：** 时段写在 `periods[]`，默认排成等宽色带，每栏一个阶段。属于并行项目时写 `lane`（项目或负责方）：色带和文字能占满各行才画泳道时间轴，否则仍用色带，并把项目写进栏标题。`label` 不是日期时补 `span`。只有一个数字时写 `data[].note`，或让它和一句话的标签模块相邻，数字收紧成小矩形，话术排在后面。一排 2–5 个数字时色块贴合内容：占满整行时数字自动放大到最满的色块撑满为止；数字太短撑不满时色块按内容收窄，相邻的一句话标签模块接在同一行。没有相邻句子时：色块小、接近正方形就整组左右居中；色块是宽矩形，就排成横跨整行的长条：最重要的数字（`highlight` 或标题提到的，否则第一个）占最宽的深色色块，所有数字统一放大（约两倍，色块放得下为止），其余色块并排、宽度贴合内容。一组 3–5 个、没有目标值的数字有两种排法：色块，或锚定指标带（最重要的数字放进左侧实心块，其余在浅色带上并排，用细竖线分隔，所有数字同一字号，横跨整行）。组版器先按数据选：标题点到或标了 `highlight` 的数字用指标带，否则用色块；再按整份稿错开，相邻两个有数字组的页面不用同一种。指标带的标签太长时换成两行。数字组和别的模块并排时，指标带竖过来：重点数字在上方实心块，其余逐行列出，标签在左、数字在右。数字组和一句话标签并排、页面上还有第二组数字、或指标带让页面放不下时，保持色块。要固定某页的排法就写 `figureStyle:'tiles'` 或 `'strip'`。并列事项（`items`）同理：3–5 项、每项都有一句话、长度相近、单独占一整行时排成等宽卡片（色帽、01 编号、小标题、一句话），否则用编号列表；相邻两个有事项的页面也错开。固定排法写 `itemStyle:'list'` 或 `'cards'`。说明这组数字的那句话要和 `data` 相邻：写 `order` 时把这句话放在 `metrics` 前面（如 `['benchmark','metrics','table']`），写在 `metrics` 后面会被当成页底收尾句，不会接到同一行。数字拆进色块后，相邻的句子要能单独读通：比较句保留原文主语（写“单台成本远低于信息流”，不要只剩“成交 12 台，远低于信息流”）。内容铺不满时整组上下居中。`data[].target` 写目标值：一页只有一个目标时排成“目标 → 实际”，有多个时目标写在各自色块里，不自动算完成率。整行排开的一排数字色块不用图标填空：只有同组每个数字都写了 `data[].icon` 才显示图标（名称见 `outline:check` 提示），否则整组都不带。和其他模块并排、折成两行的色块，空余较大时仍会整组自动带图标；封面色块不带。照片 `src` 用相对路径时给组版器传 `baseDir`；带标签的一句话写 `statements:[{id,label,text,from}]`（复盘判断等收尾句自动放页底并用跳色）；短语式结果加 `asMetric:true`；动作写 `items`，`title` 是 2–6 字短标签，`detail` 是完整原句，`itemsHeading` 写概括；流程写 `flows`/`chains`，步骤可带 `{title,detail}`，`title` 写模块名；表格 `table.highlight` 标重点行，一页两张表写 `tables:[{title,columns,rows,highlight,from}]`（区域 `table-1`、`table-2`）；回到前面某步的流程写 `returnTo:步骤序号`，自动画回流线；数字色块只在 `data[].highlight:true` 或标题提到该项时强调，否则一律不强调；`compare`（`leftLabel`、`rightLabel`）放对照；`periods` 放时期；`eyebrow`、`focus` 控制页头，`X：结论` 式标题自动拆开；标题没有逗号时必须写 `focus`（返回的 `focusGuessed` 会列出这些页）。
   - **页头页尾：** 组版器自动生成，不手写。页头是实心标签（`eyebrow`，没写时按页面角色取，带页序）加同行标题，下方细线上的粗段表示进度；`header:'eyebrow'` 改成小字标签在标题上方。页脚是细线、来源和 `01 / 05` 页码；来源只写材料名称和时期，定稿、版本、字体规范这类内部字样不上屏，组版器也会自动去掉。
   - **板块：** `compare` 写两侧（`leftLabel`、`rightLabel`、`left[]`、`right[]`）。两侧是同一组指标且每项都是数字时（`left[i].title` 与 `right[i].title` 相同，`detail` 写 `260 元` 这样的数值，2–5 项），排成一排变化色块，每块一行“前值 → 后值”，后值放大，标题提到的那一项整块反白；数值对比一律这样写，不要把前后数字写成两列正文。其他情况排成左右两栏：条数相同按 `left[i]` 对 `right[i]` 逐行对齐，前后或问题对改进的关系中间画箭头，其余逐行对照用编号；条数不同（或写 `paired:false`）两侧各自成列，中间不加标记。代表本期或改进方向的一侧用主色，另一侧用辅色，按标签判断（去年/今年、上半年/下半年、问题/改进、年份），判断不了或要指定时写 `current:'left'|'right'`。问题对改进是对应关系，不加 VS；确实是对立的两方才写 `badge:'VS'`。`periods` 出箭头色带，每段 `title` 加逐条 `points`；逐行有多列信息时仍用表格，表里有“占比 / 比例”列且是百分数时，这一列原地画成比例条（合计行不画），其他列照原样；`data[].highlight` 的色块整块反白。
   - **封面：** 大纲第一页写 `role:'cover'`，`keyLine` 是这一期的整体状态句，`name` 是稿件名（默认取大纲 `title`），可带 `eyebrow`、最多 3 个 `data`（写了 `target` 的在色块里显示目标，和内容页同一个数字口径一致；色块按内容收窄，数字放大到和状态句同一字号，不加图标）、1 张 `photos`，`focus` 标出状态句里的重点。封面不计页码，不要手写。
   - **阅读顺序：** 默认按页面角色排；模块先后不合内容关系时写 `order:['flow-1','items','verdict']`，组版器照这个顺序排，写在第一个模块之前的句子放页头，之后的放页底，比手写 `layouts` 更安全。内容放不下时组版器会自动换排法（并排、把模块挪到照片旁），用了哪种列在返回的 `rearranged`，一般不用手写。确实要指定并排关系时才传 `layouts`（排不下或叠压时组版器会直接报错）：`layouts:{p2:[{left:['problem','items','metrics'],right:'photos'},['verdict','tool']]}`。
   - **断行：** 组版器自动处理文字框断行：最后一行不超过 4 个字、或一个词被拆到两行（如“转介/绍率”）时，把文字框最多收窄四分之一重新分行，优先断在顿号、逗号后面，不增加行数。仍改不过来就改写这句话，不手动插换行。
   - **字阶：** 板块高度贴合内容，不为铺满页面把色块、表格、流程拉高。同一行并排的板块：内容量接近的画成等高；一句话标签这类内容少得多的（自身高度不到这一行的 65%）按内容取高，上下居中。两种不同模块并排时分主次：标题里的数字或 `focus` 落在哪个模块，哪个模块占宽栏（约 53%–60%）；标题没提到时内容多的占宽栏；同类模块（两张表、两条流程）仍等宽。一页有两组数字色块时，含标题数字的一组保持原字号，另一组数字缩到约四分之三；标题都没提到时成果数字为主。页面有余量时整页提高一档字号（20、22、24、26，内容极少时 30），选放得下的最大一档，层级比例不变。放得下但偏空的页会自动试其他排法。返回的 `sparse`（内容太少）和 `loose`（上下留空超过四分之一，`make` 同样提醒 `page-body-loose`）列出仍然偏空的页，要合并页面或补内容，不直接交付。所有排法都放不下时才报错，这时按提示拆页或减少模块，用户指定过页数的先看能否精简模块。
   - **规则清单和定位句：** 组版后调用 `draftDeckClaims({deck,outline,palette,projectId})`，按实际放置的元素生成 `throughLine` 和 management-report 的规则清单（证据指向真实元素，不要手写元素编号）。生成的是草稿，要按成稿逐条核对 `how`，不成立的改掉；其他场景按 `rules:checklist` 写。
   - **大纲写法是结构信号，不是版面：** “导语：”“业务问题：”这类标签不印成句首前缀，转成模块标签；括号说明去掉括号做小字；箭头链写成流程。
7. **生成与检查（原规则 step4）：** `make <authored.json> <用户命名.html> --screenshots <临时目录> --summary`。`make` 只接受声明了四项内容契约、同目录有 `content-baseline.json` 的新稿，否则以 `new-deck-contracts-required` 或 `content-baseline-file-missing` 拦下，不建工程。逐页实际看图，按原规则的 7 项看图清单和 [复核清单](references/fusion/visual-review.md) 修正（局部修改用 `patch:project`）。新稿首次 `make` 会以 `rules-review-missing` 停下，然后进入独立复核。工程建好后没有经过 `patch:project` 或网页编辑时，可以用同一个 `projectId` 重跑 `make`；有人工修改或已正式发布时 `make` 会拒绝，防止覆盖。`ok:false` 时没有 `outFile`，表示 HTML 还没写出。
8. **独立复核（同一轮内闭环）：** `review:rules <workspaceDir>`。有 fail 时不结束本轮、不向用户汇报“未通过/还不能交付”：直接按理由改页面（`patch:project`），重新 `review:rules`，最多 3 轮。涉及版式、精致度、结构图、视觉母题的 fail 必须重新构图（换布局、加结构图或母题、调整图片面积），并更新 `visualDecision.layout`；只改措辞、行距或字号不算修正。通过后 `publish:html <workspaceDir> <交付.html>`（见“独立复核”）。
9. **交付（原规则 step5 由 Dawang 替代）：** 只交付一个 HTML（见“交付与保存”）。回复开头依次写（关系缺口直接用 `outline:check` 的 `deliveryNote` 段落，只删不成立的条目，不改写成一句话摘要）：
   - **关系缺口**（未授权时）：挑最影响判断的几条，不用字段名，不压缩成“第 N 页缺 X”。每条单独成段，写清四件事：哪一页、材料里有什么、缺的关系用读者的问题说出来、补上后页面会变成什么。例如：“第 3 页，48 单算好还是差？材料只有实际数，没有目标或去年数，领导没法判断。给我目标值就行，比如目标 50 单，这页就能改成目标与实际对照。”最后加一句可以先按常见逻辑补上、用户再改。
   - **补写清单**（已授权时）：按 `publish:html` 结果的 `drafted` 逐页列出补写的实际文字和 `XX` 占位，不只写类别（写“第 3 页原因：客户需求分层不够细”，不写“第 3 页：原因分析”），请用户核对修改，并告诉用户编辑器侧栏和导出 PPTX 的演讲备注里也标了这些内容。
   - **展开说明：** `drafted` 里 `kind:'expanded'` 的条目逐页列出，说明这是制作时展开的，请用户核对。
   - **配色预览**（未指定、未委托时）：说明本版用了哪组、为什么，附备选预览。

   之后列出 contentReview（定位句、每页重点句及来源，created 句请用户确认）、visualReview 每页视觉重点、ruleReview 未采用的规则及理由、复核轮次与 fail→修正；用户决定覆盖了哪些检查（结果里的 `decided`、复核的 `decided`），以及第 3 轮后仍未解决、带着交付的复核意见（`rules-review-open`）逐条写明，请用户决定。用户效果认可单独记录。未经要求不加演讲者备注。

## 规则清单

`rules:checklist <场景>` 按章节列出主场景文档与通用 Requirements（`scenario#章节`、`general#Requirements`），每章附原文要点 `sections[].rules` 与待填骨架。逐条读完要点后，每章写一条到 `contentPlan.ruleChecklist:{scenario,items}`：

- `applied`：写 `how`（这一章的要求在本稿怎么落实，覆盖章内要点）与 `evidence:[{slideId,elementIds}]`，指向实际承担的元素。
- `not-applicable` / `user-override`：写 `reason`（如大纲指定配色属于 user-override；风格参考章节本稿未借用）。

任一章未记录，`make`/`publish:html` 失败；过半未采用会警告。

**Dawang 版式例外按子规则记录：** 原规则里被用户替换的个别条款（禁止卡片、禁止均分、统一圆角、场景配色、AI 配色）列在 [Dawang 版式例外](references/fusion/house-style.md) 表里，编号 HS-01…HS-05，每条写明现在允许什么、仍然要求什么。涉及的章节照常记为 `applied`，在 `how` 里写其余要求怎么落实，并引用编号（如“数字色块与结论条按 HS-01，并列指标等宽按 HS-02”）；**不要把整章记成 `user-override`**，那会把同章里无关的要求（如顶级视觉、母题）一起关掉。复核者按这张表判断这些条款。旧工程沿用逐条清单（`rules:checklist <场景> --items`）。

## 独立复核

程序只能证明每条都有记录、证据指向真实元素；是否真的做到，由复核者判定：

- `review:rules` 截图全稿，把截图、元素表、原规则和清单声明交给一个全新上下文的复核者（默认本机 Codex CLI，只读、不留会话；`DAWANG_REVIEWER_CMD` 可换成其他命令，`DAWANG_REVIEWER_MODEL` 指定模型），逐条判 pass/fail，写入工程的 `rules-review.json`。除规则外，复核者还按三条视觉标准看图：对齐（节点与说明、同行图片、数字与单位）、主次（第一眼是否读到重点、是否每页同构）、图片（关键区域看得清、未变形、无大块空白）；fail 会写出页码和具体问题。
- 不得为了通过复核而去掉数字色块、色块图标、深色侧栏或照片拼板，也不得把裁切嵌入的照片改成完整显示或缩小（裁切意见只调 `focal` 或换图）；复核因这些组件判 fail 时，检查清单对应章节的 `how` 是否引用了 HS 编号，补全后重新复核。
- 复核者看不到制作者的思考。用条形图充当结构图、页脚线充当母题、泛泛描述充当封面状态句、动作罗列充当结论标题等勉强对应会被判 fail。
- 修改后再次 `review:rules` 只复核上一轮 fail 的条目，通过项沿用（清单改动或加 `--full` 时全部重判），后续轮次更快。
- 下面放宽的只是独立复核者的意见：原规则 step4 的 7 项看图自查必须每页通过，程序检查（溢出、出界、叠压、图片未填满等）必须通过，只有用户决定能放行某项程序检查。
- `publish:html` 只接受当前修订、当前清单的复核：不通过的条目被用户决定覆盖时算已决定；没被覆盖的不通过在前 3 轮必须修改。新稿按内容、渲染、设计三类分级：事实漂移、文字裁切重叠、核心关系缺失等阻断问题，**第 3 轮后仍阻止正式发布**，用 `publish:html <工程> <交付.html> --review-draft <审阅稿.html>` 输出审阅稿并告知用户；审美类建议随正式稿交付，回复里逐条写明。旧工程沿用原规则：第 3 轮后仍未解决的意见以 `rules-review-open` 列出，不阻止发布，回复逐条写明并请用户决定。之后任何修改都需重新复核。按 fail 理由改页面；确实不适用时改为 not-applicable 并写理由（同样会被复核）。不得编辑或伪造 `rules-review.json`。没有 Codex 但宿主能开全新上下文的子智能体时，运行 `review:rules <工程目录> --prepare <新目录>` 生成复核材料，让子智能体读该目录并写出 `verdict.json`（只给目录，不告诉它制作过程），再运行 `review:rules <工程目录> --verdict <verdict.json>`。都没有时告知用户，不跳过。
- 部分页面（`scope: part`）不因缺少整体结论、下一步等整稿内容判 fail，复核提示已写明。
- fail 的原因是原材料没有、且所做页面确实需要的信息：不要改措辞反复重试，也不要停下来问用户。用户已授权补写的，把缺的内容写上；否则清单该条改为 `not-applicable`，理由写“材料未提供……，已在交付时说明”，再复核（复核会判通过），并把这项写进交付回复的关系缺口。
- 复核意见与用户已明确的决定冲突时，不要顺着复核去改页面（例如把裁切的照片改成完整显示、把图片缩小）：把用户决定写进 `requirements.userDecisions`（见下节），重新复核即可。
- 回复必须与实际状态一致：本轮结束就是停止，不写“我会继续/接下来我会/你不需要操作”而不做。要继续就在本轮继续执行；做不到就明确说已停止、停在哪里。

## 用户决定

用户在对话里做的决定优先于原规则、Dawang 做法和复核者的判断。要让这个优先级在检查和复核里生效，必须记录到 `requirements.userDecisions`：

```json
{ "id": "p3-placeholder-photos", "quote": "图片仅作示意、不必与大纲一致", "decision": "第3页保留示意图，按行与各项对齐", "covers": ["visual#images"], "pages": ["p3"] }
```

- `quote` 是用户原话，不改写成用户没说过的话；没有用户原话就不能记录决定。
- `covers` 写被这条决定覆盖的复核条目 id（如 `visual#images`、`scenario#Color Palette Reference`）或检查 kind（如 `image-small-in-zone`）；`pages` 限定页面，省略表示全稿。
- 被覆盖的检查不再阻止 `make`/`publish:html`，在结果的 `decided` 里列出；复核者能看到用户原话，按决定判断。
- 已经确认、长期有效的偏好（数字色块、先画框再裁切、九组汇报配色等）已写进技能，不需要每份稿重复记录。

## 视觉执行检查点

每页 `visualDecision:{pattern,focus:{elementId,text?},layout,zones:[{id,role,bounds}]}`。页型和组件怎么选以 `outline:check` 的建议为准（选择逻辑只在代码里维护一份），下面只写硬性要求，`make` 会检查：

1. 先按场景规则要求定标题（如管理汇报要求标题陈述状态或结论），再在其中选出重点：最值得记住的结论、状态或数值，不是动作罗列。
2. 重点是句中一段时，用同一文字元素的 runs 让它在字号/字重/颜色/字体上区别于引导语；重点自成元素时让它成为本页最大字号。`layout` 写主视觉、证据与重点的空间关系。目录、过渡页等写 `{waived:'理由'}`。
3. 不能每页都把整块标题当重点（`visual-focus-all-titles` 会拦下）：至少有页面以大数字、关键词或结构节点为重点，或用 `focus.text` 指定标题中以 runs 区分的一段。
4. 数字默认放进色块（`metricTiles`，页型已默认）：标签在上、数字在下，重点数字用强调色竖条区分，不把一排裸数字直接摆在页面上。组版器排的色块贴合内容，不靠图标填空。手写页面直接调用 `metricTiles` 时，色块空余较大会自动补图标，空间刚好则不加；同一组要么每块都有图标，要么都没有（有一块放不下就整组不加）；图标不能关闭（不写 `icons:false`），也不要为了加图标缩小数字。自己画的一排色块里每一块右侧都空余较大却没有图标，`make` 会以 `tile-spare-no-icon` 拦下：先按内容收窄色块。
5. 数据优先于图片：页面有多个数字时，数字必须进色块，不能埋进照片拼板的文字里；照片拼板 `photoPanels` 只用于文字少、几乎没有数据、每张照片对应一项的页面，拼板文字里超过 3 个数字时页型会报错。
6. **图片策略（所有照片组共用 `photoGroup`）：** 照片不拉伸，每张图的框跟着照片方向走（竖图竖框、横图横框），由工具选裁切最少的组合；照片组外边缘需要和旁边内容对齐时，先试只轻裁铺满，做不到再用裁切最少的框铺满（`listWithPhotos`）；高度可以跟着照片走时，按原图比例取图片最大的排法再轻裁对齐边缘（`itemRows`）。不要为了对称把所有照片裁成同样的框，也不要用 `fitImage` 把每张图各自缩小（`image-group-gaps`）。裁切围绕主体（`focal`），不切掉人脸和关键文字；复核说裁切切掉了内容时只调 `focal` 或换图，不改成完整显示或缩小（`image-frame-broken`、`image-letterbox`、`image-small-in-zone` 会拦下）。出现 `visual-zone-sparse` 时放大主体、收窄区域或换页型。
7. `zones` 先把页面分成几个区域（role：focus / evidence / support / flow / data / note / media），区域不重叠，页头页脚以外的文字和图片都落在区域内；`wireframe` 可预览。
8. 出现 `visual-layout-repeated` 或 `visual-text-only` 时回到构图重新分配区域，或说明内容为何要求如此。
9. 深色侧栏（需审批事项、下一步）用 `sidePanel`：标题、关键数字、编号事项按面板高度铺开，不在底部留大块空的深色；编号与缩进用工具排，不在一个文字框里用空格对齐（`text-manual-list` 会拦下）。
10. 一句收尾结论（复盘判断、下一步重点）不要单独悬在页面空白里：放进结论条 `noteBar`，贴着它总结的数据，或并入页头副标题（`text-orphan` 会拦下）。
11. **逐项对应：** 事项、数据、照片能逐项对应时落在同一列（`itemsWithPhotos`）；内容不足以逐项对应时用 `itemRows`：事项文字保持编号列表、不加底框，原来横排的数据色块改为竖排、与各自事项同行对齐，照片按第 6 条成组排列，不暗示哪张对哪项。示意照片在页脚写明，用户确认的写进 `userDecisions`。

## 交付与保存

默认交付目录只有一个用户命名的 HTML，内含可移交 ProjectV2 快照与资源，不附源目录、截图、ZIP 或报告；内部工程在 `~/.dawang-ppt/workspaces/<projectId>/`。`preview:start <workspaceDir>` 在网页工作台编辑，保留手工位置、裁切、字号及 runs。离线 HTML 顶部常驻“保存”，⌘S/Ctrl+S 与侧栏保存同一逻辑：首次关联原 HTML 并校验 projectId，之后直接覆盖；保存绝不静默下载副本，失败保留修改且不显示已保存；浏览器草稿不等于源文件保存。用户自行导出 PPTX/PDF/当前页图片，任务明确要求时可主动生成。保存与导出细节见 [工程编写速查](references/authoring-api.md)。编辑器的保存、重开、撤销重做由版本测试覆盖，单份稿件不在浏览器里重复测试；只看图检查页面本身。

## 已有工程与历史输入

- 新入口只约束 `make` 新建的稿件。旧工程不自动补声明，继续按原检查修改和发布。
- 局部修改：`patch:project` 后 `publish:html`，保留稳定 ID 与历史；严禁删除工程重建覆盖人工修改。
- ProjectV2：`render:project <deck-project.json> <index.html>`；历史 brief：`render:brief`；用户指定 dashi 原样模板：`templates` / `render:goal`（见 [旧主题与返工](references/legacy-and-revision.md)）。不承诺任意 HTML/PPTX 无损导入。
- 不支持原生数据图表、SmartArt、任意 SVG/动画；用文字、runs、图片、形状、线条和受控 vector 构建，不静默改成整页图片。

`run.json` 记最新诊断，`runs.jsonl` 追加程序阶段计时；模型思考、平台等待与返工另记，无法区分时标未知。
